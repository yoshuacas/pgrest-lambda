How to read this number

Three things bound this measurement. The first biases it, the second is left failing on purpose, and the third is a ceiling no amount of engine work moves, and the last lists what an audit found behind some of the passes.

1. Fixture isolation is per spec file, not per request

Upstream runs its suite with configDbTxRollbackAll = True (test/spec/SpecHelper.hs), so every request is rolled back and no upstream example ever sees another example's writes. That is not available here: Aurora DSQL has no SAVEPOINT and the engine holds no transaction open across a request. The runner's closest approximation is --reload-per-spec, which reloads the fixtures once per spec file and was used for this run. The size of the effect is measured, on one commit (3fbf941) with every other flag held constant: 550 of 1,199 with the flag (verified, per-spec reload) against 443 of 1,199 without it (verified, no per-spec reload). That 107-case difference is reading specs being scored against rows an earlier mutating spec left behind.

The residual bias is what per-spec reload cannot reach: a case that mutates data still changes what later cases in the same spec file read. Upstream's own ordering assumes a pristine row at every example.

The targeted reset does not remove this bias in the published number. The runner has --reset-touched, which restores only the tables a mutating case wrote to, and --reset-mutations, which re-applies the whole data fixture after every mutating case. Both default to off, both need --concurrency 1, and neither is in the flags this run was measured with (--target dsql --concurrency 1 --reload-per-spec, PGREST_RELATIONSHIPS_PATH set). A three-spec control run during verification (UpsertSpec, InsertSpec, UpdateSpec) moved cases in both directions with the targeted reset on — 11 from fail to pass and 4 from pass to fail — so it makes the measurement more faithful rather than higher. That control is not in the trend, because a three-spec run is not a suite score.

Direction of the bias: mostly downward. A read that upstream scores against pristine data is scored here against data an earlier case in the same file changed, which produces a failure, not a pass. It can also flatter a case in the other direction — a read that happens to want the mutated row — which is why the residual is called a bias and not a discount.

2. Order-dependent assertions: 12 failures kept as failures

12 cases in this run failed with the right rows in the wrong order. Aurora DSQL is distributed and keeps no heap the way PostgreSQL does, so a query with no ORDER BY comes back in whatever order the storage layer produces and insertion order is not preserved. Upstream's assertions were written against PostgreSQL, where a sequential scan of a freshly loaded table returns rows in heap order, which is insertion order — so upstream can assert a row sequence without ever writing order=. The engine adds no implicit ORDER BY, because inventing one would change its semantics for every caller in order to make a test pass.

These are counted as failures in the headline. Reclassifying them as skipped or out of scope would lift the rate on a technicality, so the report leaves them in and names them: JsonOperatorSpec:248, QuerySpec:318, QuerySpec:324, QuerySpec:338, QuerySpec:345, QuerySpec:382, QuerySpec:389, QuerySpec:571, QuerySpec:1305, QuerySpec:1313, RpcSpec:985, RpcSpec:997.

Do not read 12 as the size of the problem. Across the measured runs this count ranges from 5 to 21 (the previous run with the same flags, c718ab4 2026-08-23T06:25:20Z, recorded 15) — the order-dependent assertions are a fixed set, and how many of them happen to come back in the order upstream expects is luck. 4. What an audit of the passes found

Each wave is audited for passes that are weaker than they look, and for gains whose cause is not the one the case name suggests. No audit so far has found a pass that was not earned; what they find is how a pass was reached, which no input file can compute. Entries accumulate — one is never removed to tidy the page up, so a finding about an earlier tree stays here and says which tree it was about. 8 findings, oldest first:

  • 3 of the passes cannot tell their setting apart. The harness now boots PreparedStatementsSpec twice, once with db-prepared-statements=true and once with false, and all three of its cases pass both ways. They pass because nothing in src/rest/ reads that setting: it is parsed in src/index.mjs and put on the request context, and no query path consults it (grep -rn dbPreparedStatements src/ returns two hits, neither in the engine). PreparedStatementsSpec:25 asserts a bare 200, so it cannot distinguish the two values even in principle. Read those three as "the switch is accepted", not "prepared statements behave as upstream". docs/reference/configuration.md documents the setting as inert.
  • 23 of the gains on tree 2488109 rode on the data-representations manifest, not on catalog reading. DSQL rejects CREATE CAST, so all 15 casts upstream's schema.sql defines are dropped at fixture load and pg_cast reports nothing for the engine to read. conformance/fixtures/representations.json declares those 15 pairs and the runner points PGREST_REPRESENTATIONS_PATH at it by default for --target dsql. 23 cases that were failures in the run before tree 2488109 passed there because of it — ComputedRelsSpec:110/123/129, QuerySpec:1549…1650 (16 cases), InsertSpec:802 and UpdateSpec:649/660/682. The manifest is a substitute for a catalog DSQL cannot populate, exactly like the relationship manifest, and it is not tuned to pass everything: 11 data-representation cases still fail with it in place. But a reader is entitled to know that 23 of that wave's gains were configuration-enabled, and that on a database with pg_cast the engine reads them from the catalog instead.
  • On tree 2488109 the full-text-search feature row moved 6 cases on row order, not on text search. The feature table read 14 of 47 for fts/plfts/phfts/wfts on tree 2488109 and 8 of 47 in the publication before it. None of that is a text search change. Six of those cases assert an unordered result set and pass only on the runs where DSQL happens to return the rows in upstream's sequence: QuerySpec:75, :80, :338, :345, :382, :389, plus RpcSpec:985 and :997, which the runner now files as order-dependent rather than as a missing configuration. Read that row as "between 8 and 14 of 47". DSQL still ships one text search configuration, simple, and every remaining failure in the gap is its.
  • The most important fix on tree 2488109 is invisible to this measurement. buildAuthzFilter in src/rest/cedar.mjs discarded every forbid in a policy set whenever any permit granted the table unconditionally — in both policy orders, not intermittently — so a deployment whose policies read "permit reads of this table, forbid the archived rows" served the archived rows. It is fixed, with regression tests confirmed to fail against the old code. No case in this report exercises it, because no upstream PostgREST case uses a Cedar forbid: upstream has no Cedar. It was found by reading the code the Cedar equivalence measurement runs through, not by either measurement. Take it as a limit on what a flat pass rate tells you about a wave, in both directions.
  • Two corrections were made to the case files themselves. The rule for this suite is that conformance/cases/ is never edited to make a test pass. Both changes here are to the extractor, and both are checkable against the upstream source. First, makeResolver in conformance/extract/parse-spec.mjs picked a let jwtPayload binding by absolute line distance, so an it block ending in a bare shouldRespondWith 200 took the next block's binding. AudienceJwtSecretSpec:32 ("succeeds when the audience claim matches") carried aud: "notyouraudience" where AudienceJwtSecretSpec.hs:29 has "youraudience", so a correct engine could not pass it. Haskell let is lexical; the resolver now prefers the nearest binding at or above the use site. Re-extraction changed exactly one case file and all 19 of its cases now match the upstream source one for one. Second, the fixtures load upstream's test schema into public and the extractor already rewrites test. to public. inside an expected error body — but it left the Content-Length assertion at upstream's byte count, so a byte-exact engine failed on the length of a schema name. The count is now adjusted by the two bytes each rewrite adds, which is 9 cases: ErrorSpec:43/81/89/98, QuerySpec:32, RpcSpec:212/271, UpdateSpec:17/359. That tightens the assertion rather than dropping it — the length still has to be exact — and each affected case records the adjustment in its own transforms list. QuerySpec:629 also asserts a Content-Length and is not touched: it is 10 bytes short of upstream on a body the schema rename never saw, and it stays a failure.
  • 41 of this run's gains are isolation, bought by running the engine the way upstream runs it. Upstream's SpecHelper.hs sets configDbTxRollbackAll = True and configDbTxAllowOverride = True for every spec — db-tx-end = rollback-allow-override — so every mutating request its suite makes is undone unless that request asks for Prefer: tx=commit. The engine now implements the same option and the runner sets the same value, so a mutating case stops changing the fixtures the cases after it read. That is where 41 of the id-matched gains in this run come from: UpdateSpec (9), InsertSpec (6), UpsertSpec (6), NullsStripSpec (5), MaxAffectedSpec (4), MultipleSchemaSpec (4), AndOrParamsSpec (3), DeleteSpec (2) and SingularSpec (2). None of them is a new query feature — they are assertions that were being read against data an earlier case had already changed. The engine's own default is db-tx-end=commit, and a deployment on the default gets none of this isolation and does not need it. Two consequences worth stating: the same tree measured with commit scores lower for a reason that is about the harness rather than the engine, and the setting therefore belongs beside the flags — it is recorded in compatreport/README.md with the rest of the runner's base engine configuration, next to bulkMutationGuard: 'off'.
  • 18 more gains are the JWT path being measured for the first time. Until this run the harness built the API Gateway authorizer context by decoding the JWT payload without verifying it, while upstream configures jwt-secret for every spec and PostgREST verifies on every request. A token signed with the wrong secret therefore reached the table: the specs asserting a rejected token could not fail, which is what the harness-supplies-unverified-identity gap was, and the ones asserting an accepted token passed without the check being exercised. The runner's base engine now runs with rest-jwt and upstream's own secret. 18 cases gained — 8 in ErrorSpec, 8 in AuthSpec, 2 in AudienceJwtSecretSpec — and closing them needed engine work as well as harness work: the decode-error vocabulary (Error.hs message (JwtDecodeErr e), which the specs assert by string) and registered-claim validation (Auth/Jwt.hs checkForErrors — exp, nbf, iat, aud in that order, a present-but-non-numeric claim beating expiry, 30 seconds of skew both ways). Read the 18 as "this path is now measured", not as "this path got faster to fix": before this run neither a pass nor a failure here said anything about token handling.
  • 4 gains are a fixture the transform used to drop whole. Upstream fills public.contract with its only INSERT ... SELECT, and one of the columns it writes is a tsrange DSQL will not store. The transform could cut a dropped column out of a VALUES tuple but not out of a select list, so it dropped the statement and the table stayed empty — and four embed assertions that read it (QuerySpec:962/969/977/984) could not pass for want of rows. The transform now cuts the select list positionally the same way. This is the same class of gain as the relationship and data-representation manifests: fixture fidelity, not engine behaviour. It differs from them in one way worth the distinction — it restores upstream's own data rather than substituting for a catalog DSQL cannot populate.

Editorial, like the gap notes: an audit finding is a judgement about a cause, and causes are not in the results file. Each one names what was run so it can be checked. None of them changes a status, and none is netted off the rate — they change what the rate means, not what it is.

  11. 12 row-order-unspecified out-of-scope in pass rate

    Same rows, different order. Upstream emits no implicit ORDER BY: a read with no order= returns rows in PostgreSQL's scan order, which on a freshly loaded table is insertion order, stable enough that upstream's expectations encode it. DSQL promises no physical order, so the same read can come back two ways. The engine now appends the relation's primary key to every ORDER BY (PGREST_DETERMINISTIC_ORDER, on by default), and for a relation with no primary key it appends every column PostgreSQL can order by. That did not shrink this gap — the count of order-only failures has been 12 to 15 with the tiebreak and was 7, 13, 19 and 19 across four runs of the tree before it — what it did was stop the rest of the suite moving: the widest spread between runs of one tree was 12 cases before it (1068 to 1080 on tree 2488109) and has been 1 case and then 0 on the two trees measured since. Read the tiebreak as buying repeatability, not passes. Three cases in this gap were never DSQL's order. QueryLimitedSpec:97, :108 and UpdateSpec:444 ask a mutation to order the representation it returns (order=last_name on a bulk PATCH and on a DELETE, order=a.desc on an UPDATE), and the engine dropped the order: it built the representation from the statement's own RETURNING list, which has no ORDER BY to put it in. Upstream plans every mutation's representation as a read over the source CTE (Plan.hs mutateReadPlan, and the addRels root case that re-points it at pgrst_source), which is where the order goes; the engine now does the same whenever the request orders or embeds, and all three pass. That was an engine defect this gap was hiding, and it is the reason the gap reads 12 here and 15 in the run published before it. What is left is 12 cases, and every one of them is a relation with no primary key whose rows were inserted in an order no column sorts into: tsearch_to_tsvector (text_search text, jsonb_search jsonb) 8 — six direct reads and two through /rpc/get_tsearch_to_tsvector — w_or_wo_comma_names (name text) 2, no_pk (a, b) 1 and json_table 1. json_table is the one the tiebreak cannot reach at all: its only column is data json, a type PostgreSQL will not order by, so nothing is appended and the rows that carry no foo key stay tied — which is why JsonOperatorSpec:248 passed in one earlier run of a tree whose other runs failed it, and why this count can still move by one. Nothing derived from the data reproduces insertion order here, and the one mechanism that would — physical order via ctid — DSQL refuses outright: SELECT ctid FROM w_or_wo_comma_names answers cannot retrieve a system column in this context (probed on the conformance cluster). 8 of the 12 passed in the last run before the tiebreak and fail in every run with it: they came back in upstream's order by luck then and are sorted the wrong way consistently now, which is the trade the tiebreak makes — a stable wrong answer over an unstable right one. All 12 are counted as failures here, not hidden.

What a reader should not read into it

  • It is not a PostgREST pass rate and is never added to one. The upstream cases it derives from are in this report's denominator on their own merits — not excluded, not marked out of scope and not skipped — and where they pass there, they are counted there once and only there.
  • A holding equivalence means a Cedar permit standing in for a GRANT produced the same status, body and asserted headers. It does not mean row-level security was exercised: the table behind most of them is empty in the fixtures, so the asserted body is [] and no row was filtered either way.
  • The denominator is the derived cases, not the upstream cases they cover. The ones with no fair equivalent are in neither this numerator nor this denominator; the rate above still judges them on upstream's own assertion, and the table below says how they land there.
  • It has no external referee. This project chose which cases are about authorization, wrote the policy set and wrote the runner. The PostgREST rate above has upstream's own assertions as the referee; this number does not.
