How to read this number

Three things bound this measurement. The first biases it, the second is left failing on purpose, and the third is a ceiling no amount of engine work moves, a fourth records what left the denominator since the comparable run, and the last lists what an audit found behind some of the passes.

1. Fixture isolation is per spec file, not per request

Upstream runs its suite with configDbTxRollbackAll = True (test/spec/SpecHelper.hs), so every request is rolled back and no upstream example ever sees another example's writes. That is not available here: Aurora DSQL has no SAVEPOINT and the engine holds no transaction open across a request. The runner's closest approximation is --reload-per-spec, which reloads the fixtures once per spec file and was used for this run. The size of the effect is measured, on one commit (3fbf941) with every other flag held constant: 550 of 1,199 with the flag (verified, per-spec reload) against 443 of 1,199 without it (verified, no per-spec reload). That 107-case difference is reading specs being scored against rows an earlier mutating spec left behind.

The residual bias is what per-spec reload cannot reach: a case that mutates data still changes what later cases in the same spec file read. Upstream's own ordering assumes a pristine row at every example.

A worked example from this run, not a hypothetical. UpsertSpec:417 failed:

body (exact) mismatch:
  expected: [{"name":"Java","rank":1}]
  actual:   [{"name":"Java","rank":2}]
  at $[0].rank: expected 1, actual 2

Earlier cases in the same spec file write that row with the other value and no later case restores it, so the read is scored against a database upstream never sees. Upstream never hits this because it rolls the row back before the next example starts.

The targeted reset does not remove this bias in the published number. The runner has --reset-touched, which restores only the tables a mutating case wrote to, and --reset-mutations, which re-applies the whole data fixture after every mutating case. Both default to off, both need --concurrency 1, and neither is in the flags this run was measured with (--target dsql --concurrency 1 --reload-per-spec, PGREST_RELATIONSHIPS_PATH set). A three-spec control run during verification (UpsertSpec, InsertSpec, UpdateSpec) moved cases in both directions with the targeted reset on — 11 from fail to pass and 4 from pass to fail — so it makes the measurement more faithful rather than higher. That control is not in the trend, because a three-spec run is not a suite score.

Direction of the bias: mostly downward. A read that upstream scores against pristine data is scored here against data an earlier case in the same file changed, which produces a failure, not a pass. It can also flatter a case in the other direction — a read that happens to want the mutated row — which is why the residual is called a bias and not a discount.

2. Order-dependent assertions: 16 failures kept as failures

16 cases in this run failed with the right rows in the wrong order. Aurora DSQL is distributed and keeps no heap the way PostgreSQL does, so a query with no ORDER BY comes back in whatever order the storage layer produces and insertion order is not preserved. Upstream's assertions were written against PostgreSQL, where a sequential scan of a freshly loaded table returns rows in heap order, which is insertion order — so upstream can assert a row sequence without ever writing order=. The engine adds no implicit ORDER BY, because inventing one would change its semantics for every caller in order to make a test pass.

These are counted as failures in the headline. Reclassifying them as skipped or out of scope would lift the rate on a technicality, so the report leaves them in and names them: JsonOperatorSpec:248, QueryLimitedSpec:97, QueryLimitedSpec:108, QuerySpec:75, QuerySpec:80, QuerySpec:338, QuerySpec:345, QuerySpec:382, QuerySpec:389, QuerySpec:1265, QuerySpec:1282, QuerySpec:1305, TimezoneSpec:15, TimezoneSpec:25, TimezoneSpec:61, TimezoneSpec:71.

Do not read 16 as the size of the problem. Across the measured runs this count ranges from 5 to 21 (the previous run with the same flags, eeb1ac9 independent re-measurement, recorded 11) — the order-dependent assertions are a fixed set, and how many of them happen to come back in the order upstream expects is luck. 5. What an audit of this run found in the passes

An independent pass re-measured this tree and went looking for passes that are weaker than they look. It found no inflation in the rate — its own run scored higher than the one published here — but it did find two things about how some passes are reached that no input file can compute. Both are recorded here rather than in a commit message:

  • 3 of the passes cannot tell their setting apart. The harness now boots PreparedStatementsSpec twice, once with db-prepared-statements=true and once with false, and all three of its cases pass both ways. They pass because nothing in src/rest/ reads that setting: it is parsed in src/index.mjs and put on the request context, and no query path consults it (grep -rn dbPreparedStatements src/ returns two hits, neither in the engine). PreparedStatementsSpec:25 asserts a bare 200, so it cannot distinguish the two values even in principle. Read those three as "the switch is accepted", not "prepared statements behave as upstream". docs/reference/configuration.md documents the setting as inert.
  • 23 of the gains ride on the data-representations manifest, not on catalog reading. DSQL rejects CREATE CAST, so all 15 casts upstream's schema.sql defines are dropped at fixture load and pg_cast reports nothing for the engine to read. conformance/fixtures/representations.json declares those 15 pairs and the runner points PGREST_REPRESENTATIONS_PATH at it by default for --target dsql. 23 cases that were failures in the last comparable run pass because of it — ComputedRelsSpec:110/123/129, QuerySpec:1549…1650 (16 cases), InsertSpec:802 and UpdateSpec:649/660/682. The manifest is a substitute for a catalog DSQL cannot populate, exactly like the relationship manifest, and it is not tuned to pass everything: 11 data-representation cases still fail with it in place. But a reader is entitled to know that 23 of this wave's gains are configuration-enabled, and that on a database with pg_cast the engine reads them from the catalog instead.

Editorial, like the gap notes: an audit finding is a judgement about a cause, and causes are not in the results file. Each one names what was run so it can be checked. Neither changes a status, and neither is netted off the rate — they change what the rate means, not what it is.
