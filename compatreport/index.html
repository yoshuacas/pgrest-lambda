This is a partial result. The engine passes 550 of the 1,199 upstream assertions that ran and are in scope. That is +415 cases against the baseline run (2026-08-19T10:44:42Z, 135 of 1,153). The two runs used different runner flags, so 11.7% → 45.9% is not a like-for-like comparison and is not the claim being made — see Progress since the baseline for the flag-matched figure. Do not quote a higher figure: the denominator already excludes everything Aurora DSQL or this architecture makes unmeasurable.

Of the 649 failures, 566 (87.2%) are engine-side gaps that DSQL does not block, 67 come from something Aurora DSQL does not provide, where the engine has to supply the substitute itself or there is none (no-set-role (43), missing-operator-fts (24)), and 16 assert behaviour this architecture does not promise. The ten largest gaps account for 319 failures (49.2%), so the number moves in large steps, not by grinding.

Categories with zero passing cases: observability, http-headers, options.

  11. 28 no-foreign-keys engine-fixable in pass rate

    DSQL stores no foreign keys, so pg_constraint reports none and the engine reads its relationships from the declared manifest instead (PGREST_RELATIONSHIPS_PATH, reconstructed by the fixture transform into conformance/fixtures/relationships.json). What is left is what a manifest of foreign keys cannot express: cases where upstream derives a relationship from a function returning SETOF a table (PostgREST calls these computed relationships), disambiguation cases that need more than one relationship between the same pair of relations, and one case whose table is partitioned and therefore absent on DSQL. Run without the manifest, this gap is 189 failures instead — the trend above keeps that run for comparison.
