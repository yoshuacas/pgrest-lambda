How to read this number

Three things bound this measurement. The first biases it, the second is left failing on purpose, and the third is a ceiling no amount of engine work moves.

1. Fixture isolation is per spec file, not per request

Upstream runs its suite with configDbTxRollbackAll = True (test/spec/SpecHelper.hs), so every request is rolled back and no upstream example ever sees another example's writes. That is not available here: Aurora DSQL has no SAVEPOINT and the engine holds no transaction open across a request. The runner's closest approximation is --reload-per-spec, which reloads the fixtures once per spec file and was used for this run. The size of the effect is measured, on one commit (3fbf941) with every other flag held constant: 550 of 1,199 with the flag (verified, per-spec reload) against 443 of 1,199 without it (verified, no per-spec reload). That 107-case difference is reading specs being scored against rows an earlier mutating spec left behind.

The residual bias is what per-spec reload cannot reach: a case that mutates data still changes what later cases in the same spec file read. Upstream's own ordering assumes a pristine row at every example.

A worked example from this run, not a hypothetical. UpsertSpec:417 failed:

body (exact) mismatch:
  expected: [{"name":"Java","rank":1}]
  actual:   [{"name":"Java","rank":2}]
  at $[0].rank: expected 1, actual 2

Earlier cases in the same spec file write that row with the other value and no later case restores it, so the read is scored against a database upstream never sees. Upstream never hits this because it rolls the row back before the next example starts.

The targeted reset does not remove this bias in the published number. The runner has --reset-touched, which restores only the tables a mutating case wrote to, and --reset-mutations, which re-applies the whole data fixture after every mutating case. Both default to off, both need --concurrency 1, and neither is in the flags this run was measured with (--target dsql --concurrency 1 --reload-per-spec, PGREST_RELATIONSHIPS_PATH set, PGREST_REPRESENTATIONS_PATH defaulted). A three-spec control run during verification (UpsertSpec, InsertSpec, UpdateSpec) moved cases in both directions with the targeted reset on — 11 from fail to pass and 4 from pass to fail — so it makes the measurement more faithful rather than higher. That control is not in the trend, because a three-spec run is not a suite score.

Direction of the bias: mostly downward. A read that upstream scores against pristine data is scored here against data an earlier case in the same file changed, which produces a failure, not a pass. It can also flatter a case in the other direction — a read that happens to want the mutated row — which is why the residual is called a bias and not a discount.

2. Order-dependent assertions: 21 failures kept as failures

21 cases in this run failed with the right rows in the wrong order. Aurora DSQL is distributed and keeps no heap the way PostgreSQL does, so a query with no ORDER BY comes back in whatever order the storage layer produces and insertion order is not preserved. Upstream's assertions were written against PostgreSQL, where a sequential scan of a freshly loaded table returns rows in heap order, which is insertion order — so upstream can assert a row sequence without ever writing order=. The engine adds no implicit ORDER BY, because inventing one would change its semantics for every caller in order to make a test pass.

These are counted as failures in the headline. Reclassifying them as skipped or out of scope would lift the rate on a technicality, so the report leaves them in and names them: JsonOperatorSpec:248, QueryLimitedSpec:97, QueryLimitedSpec:108, QuerySpec:318, QuerySpec:324, QuerySpec:338, QuerySpec:345, QuerySpec:382, QuerySpec:389, QuerySpec:1265, QuerySpec:1282, QuerySpec:1313, QuerySpec:1427, SpreadQueriesSpec:65, SpreadQueriesSpec:78, TimezoneSpec:15, TimezoneSpec:25, TimezoneSpec:61, TimezoneSpec:71, UpdateSpec:120, UpdateSpec:539.

Do not read 21 as the size of the problem. Across the measured runs this count ranges from 5 to 21 — the order-dependent assertions are a fixed set, and how many of them happen to come back in the order upstream expects is luck. Counts per measured run:
